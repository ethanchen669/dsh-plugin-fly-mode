# 案例复盘：某网球小程序「性别字段死锁」导致账号无法报名

> 对应框架：`SKILL.md` §1–§3 · 五阶段全文：`playbook.md` · 清单：`checklist.md`
>
> 一句话：**一个从建号起就为空、且现网没有任何写入路径的必填字段，挡在报名流程前面。**
> 用户折腾了一周，背后是**三处独立缺陷**，任何一处单独存在都不至于卡死。
>
> 脱敏说明：本文只保留**方法与结构**。账号 / 订单 / 赛事 / 交易流水等一律写成占位符
> （`<会员ID>` / `<订单号>` / `<赛事ID>`），域名写成 `<业务域名>` / `<静态资源域名>`，
> 时间戳只保留日期形状。原始抓包与原始工单留在案例工作区，不进仓库。

## 1. 最终结论

| 层 | 缺陷 | 证据 |
| --- | --- | --- |
| **S1 渲染** | 性别为空时，选择器按选项第 0 项渲染成"男" | 注入 `1` → 界面变"女"；注入 `"0"` → 界面变"男"。证明显示源就是这个字段 |
| **S2 提交** | 该页面**没有性别编辑控件**；保存校验在本地 `return`，**请求根本不发出** | 全流程抓包：对业务域名的非 GET 请求**只有**一个赛事查询接口 |
| **S3 存储** | 资料更新接口的字段白名单里**没有该字段** | 改前 / 改后 diff：省 / 市 / 地址等字段全部落库、"最后修改时间"更新，**目标字段纹丝不动** |
| **G 闸门** | 报名预检接口返回 `state:false` 拦住客户端 | `{"state":false,"confirm":true,"Y":"去补充","info":"您的性别未填写，是否去补充？"}` |

**编码约定（实测）：`0 = 男`，`1 = 女`。**

## 3. 关键转折点（最值得复用的三招）

### ① 文案搜索定层（30 秒，省一天）

把报错原文丢进全部响应体搜。搜到 = 服务端判定；搜不到 = 纯前端文案。
本案例两句文案分属两层，一下就拆成了两个独立子问题。

### ② 诱出法（Inducement）

前端校验拦住不发包时，你拿不到接口格式。**篡改上游响应让校验放行**，
前端就会主动把那条本不会发出的请求交给你 —— 接口名、完整字段、编码，一次全拿到。

即使最终发现服务端不落这个字段，这次诱出也**没有白做**：它把"哪一层丢的"从猜测变成了 diff 事实。

### ③ 变更审计（改前 / 改后 diff）

一次就区分了三种可能：

| "最后修改时间" | 其他字段 | 目标字段 | 结论 |
| --- | --- | --- | --- |
| 未变 | 未变 | 未变 | 接口没被执行 / 打到了别的记录 |
| **变了** | **变了** | **未变** | **字段白名单缺失**（本案例） |
| 变了 | 部分变 | 变了 | 成功 |

配上"接口返回体是**回显请求对象**"这个反例（T4），这套组合能拆穿绝大多数"看起来成功了"。

### ④ 假值陷阱的通用钥匙（T5）

平台编码 `0 = 男`。任何 `if (!gender)` 的写法都会让"男"永久不可达 —— 这极可能就是线上 bug 的真身。
而 **JS 里字符串 `"0"` 是真值**，能同时过 `!v` 判假和 `==null` 判空；
服务端 JSON 反序列化又会把它正常转成数字 `0`。**一个字符的差别，从"永远存不进去"变成"一次写入成功"。**

## 4. 提交给厂商的工单（结构照抄，值一律占位）

> **会员 ID `<会员ID>`**（实名认证已完成：身份证、生日齐全）。
> 报名时提示"您的性别未填写，是否去补充？"，跳转资料页后性别栏显示"男"，
> 点击"保存修改"却提示"请选择性别"。
>
> **前端问题**
> ① 性别为空时按选项第 0 项渲染成"男"，误导用户以为已填写；
> ② 该页面**没有任何性别编辑入口**；
> ③ 点保存时校验在本地 `return`，**请求根本没有发出**
> （抓包确认：整个流程对 `<业务域名>` 的非 GET 请求只有一个赛事查询接口）。
> 因此退出重登、注销后找回、更换客户端、清除缓存**均不可能生效**。
>
> **后端问题（关键）**
> 通过代理注入使前端发出请求后，资料更新接口返回 `code:0`，
> 省 / 市 / 地址等字段全部成功落库、"最后修改时间"已更新，
> **但性别列纹丝不动** —— 该更新接口的字段白名单里没有性别。
> 返回体中的 `"gender":0` 只是**回显请求对象**，不是数据库中的值
> （用独立的资料读接口复查，仍为空）。
>
> **结论**
> 数据库里的性别字段自历史迁移数据起就为空；
> 现网**没有任何一条写入路径**能让用户把它填上；
> 而报名预检接口又以该字段作为报名硬门槛 → 该账号**永久无法报名**。
>
> **请执行**
> ① 修数据：`UPDATE <会员表> SET gender = 0 WHERE id = <会员ID>;`
> ② 修复项：
>    - 资料更新接口的字段白名单补上该字段；
>    - 资料页补回编辑控件，并修掉"空值被渲染成男"的误导显示；
>    - 既然报名提交并不校验性别，预检接口的性别门槛应改为非阻断或可跳过。
>
> **附带安全发现（负责任披露，未利用）**
> `<业务域名>` 的接口**鉴权不足**，仅凭一个自增数字的会员请求头
> 即可读取 / 修改任意会员资料（姓名、手机号、身份证号）。
> 另有开发遗留的占位请求头。建议尽快加固。

| 框架条目 | 本案例的来源 |

| **环境还原顺序** | 先关代理再杀进程，否则瞬断网 |
| **合规红线（不碰计费）** | 报名照常支付，只绕过坏掉的自检 |

## 6. 如果重来一次，可以更快

1. **第一步就搜响应体文案**（T2）—— 本案例绕了一圈才做，它其实能立刻把问题劈成两半
2. **诱出法应该更早用** —— 不必先纠结"怎么把字段写进库"，先让前端把请求交出来
3. **变更审计应该在第一次写入后就做** —— 能省掉中间一轮误判（"服务端返回成功码了，是不是成了"）
4. **不要先花时间找编辑入口** —— 用户的描述"没有编辑入口"已经足够定性，直接进协议层

总体路径是对的，但**第一小时的顺序可以更优**：
`搜文案定层 → 抓包定"发没发" → 诱出拿格式 → diff 定"哪层丢" → 判门禁性质 → 最小侵入达成目标`。
