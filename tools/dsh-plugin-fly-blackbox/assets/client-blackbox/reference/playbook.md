# 客户端黑盒排查 · 五阶段全文

> 这是 SKILL.md 第 3 节那张表的展开版。每阶段都有 **Gate**：没过不要往下走 —— 这是本框架最重要的纪律。
>
> 配套：`checklist.md`（可勾选清单）· `case-ttw.md`（脱敏案例）· `rules.schema.md`（规则 schema）

---

## Phase 0 · 症状分流【目标：把症状翻译成假设】

**动作**

1. 用 S1/S2/S3/G 把症状写成一句话：
   > "S1 显示 X，S2 实际提交 Y，S3 存储 Z，闸门 G 在〈前端 / 服务端〉"
2. 列出用户已尝试的无效操作（重登 / 重装 / 换设备 / 清缓存 / 换网络），**逐条解释为什么无效**。
   解释不通 ⇒ 说明模型错了，回第 1 步重写。
3. 初步判 T2：提示语出自前端还是服务端（看它像不像模板文案，还是像服务端返回的 `info` 字段）。

**产出**：一页纸的问题陈述 + 初始假设 + 待验证项清单。

**Gate 0**：能用 S1/S2/S3/G 把症状说清楚，且"为什么重登 / 重装无效"有自洽解释。

> 这一阶段最常见的错误是**跳过它**：直接去装代理。装完代理你仍然不知道该看什么，
> 于是抓一堆流量回来还是无从下手。

## Phase 1 · 建立可观测性【目标：能看见每一帧流量】

### 客户端选择矩阵（优先从上往下）

| 客户端形态 | 可抓性 | 代理行为 | 备注 |
| --- | --- | --- | --- |
| PC 客户端（Electron / Chromium 内核宿主） | ★★★ | 跟随**系统代理** | **首选**：流量与本机同源，抓包文件直接落地 |
| 浏览器 / 网页版 | ★★★ | 跟随系统代理 | 最理想，往往还能直接看 DevTools |
| iOS 真机 | ★★★ | 跟随 Wi-Fi 代理 | 需装描述文件，并在"证书信任设置"里手动打开 |
| 桌面原生应用 | ★★ | 多数跟随系统代理 | 少数自带网络栈，直接忽略代理 |
| Android 真机 | ★★ | 跟随 Wi-Fi 代理 | 用户证书可能不被信任，部分应用直接拒绝 |
| 官方开发者工具 | ★★★ | 内置 Network 面板 | 需开发权限，通常拿不到 |

> **优先选 PC 客户端**：小程序 / App 在 PC 上常跑在 Chromium 内核里，天然跟随系统代理，
> 不需要碰手机、不需要装描述文件，抓包文件就在手边。

### 搭建要点（每一步都有坑）

1. **证书目录放在工作区内**（`--set confdir=<workspace>/.fly-blackbox/mitmproxy`），别用默认的
   `~/.mitmproxy`：路径好找、好清理、好跟项目一起归档。
2. **信任 CA** 需要密码，所以是**人的动作**：用 `bx_ca command` 取那条命令自己跑，跑完 `bx_ca verify` 取证据。
3. **系统代理** HTTP 与 HTTPS **都要指向** `127.0.0.1:<port>`；`bx_sysproxy on` 会一起设。
4. **先查有没有别的代理工具在跑**（Clash / Surge / mihomo 之类常驻在本地几个高位端口）——
   它们可能抢流量。`bx_doctor` 第④段专门扫这件事。
5. **第一分钟就写还原脚本**，或者至少记下 `bx_sysproxy` 给出的那条还原命令。
6. **靶机 / 内网自签证书的上游会被默认拒绝**：mitmproxy 默认**验证上游**（`ssl_insecure: false`），
   连你自己那个自签靶也一样 —— 客户端侧看到的是我们签的证书（`issuer: CN=mitmproxy`），
   但响应是 `502`，**原因只在 mitm 日志里**（`Certificate verify failed: self-signed certificate`）。
   起代理时加 `--set ssl_verify_upstream_trusted_ca=<你的测试 CA>`（只认这一张，比 `ssl_insecure=true`
   精确）；自建靶场图省事也可以 `ssl_insecure=true`，**别对业务流量这么干**。
   判据别只写"看到 502 就以为拦截失败"：链上的签发者才是判据。

### 自检三连（Gate 1 的硬指标）

```bash
# ① HTTP 能过
curl -s -o /dev/null -w '%{http_code}\n' -x http://127.0.0.1:8080 http://example.com/
# ② HTTPS 中间人能过（这一步才是真正的验证）
curl -s -o /dev/null -w '%{http_code}\n' -x http://127.0.0.1:8080 \
     --cacert <workspace>/.fly-blackbox/mitmproxy/mitmproxy-ca-cert.pem https://example.com/
# ③ 目标客户端确实走了代理：看日志里有没有 [NEW HOST]
tail -f <workspace>/.fly-blackbox/capture/all.log
```

**只看到 ② 返回 200 还不够**：那可能是直连、也可能是另一个代理在中间。真正的判据是
**HTTPS 证书链里的签发者就是 confdir 里那张 mitm CA** —— `bx_doctor` 第②段正是这么判的。

**Gate 1**：三条全绿。特别是 ③：浏览器有流量但目标客户端没有 ⇒ 要么客户端自带网络栈忽略代理，
要么它做了证书绑定（pinning）。后者意味着此路不通，直接转 Phase 4 的人工分支。

> 教训：**在证明管道通畅之前，不要对"没抓到东西"做任何解释。** 本仓的案例里，
> 第一版脚本把 host 白名单写窄了，差点把"没流量"误判成证书绑定。

## Phase 2 · 协议测绘【目标：把黑盒变成一份接口清单】

**动作**

1. 开着代理，把目标功能的**全流程点一遍**（正常路径 + 出错路径各一遍）。
2. 输出域名分布（`bx_flows hosts`），找出**业务 API 域名**，与静态资源 CDN 分开。
3. 逐条记录：`method / path / 关键参数 / 鉴权方式 / 响应模型`。
4. **重点标注**：鉴权机制（token？签名？还是裸的会员 ID 头）、只读接口 vs 写入接口、
   预检接口（名字常含 `check` / `verify` / `pre`）。

**产出**：接口清单表。

**关键判据（T2 落地）**：把出错的提示语原文，在**全部响应体**里搜一遍
（`bx_flows grep --pattern '<提示语>'`）。搜到 ⇒ 服务端判定；搜不到 ⇒ 纯前端文案。
**这一步 30 秒，能省一天。**

**Gate 2**：能画出"用户操作 → 发出的请求 → 谁做判断"的流程图；知道提示语出自哪一层。

## Phase 3 · 三源对账 + 诱出法【目标：定位到具体那一行】

### 3.1 对账

| 对账 | 方法 | 差值说明什么 |
| --- | --- | --- |
| S1 vs S3 | 界面上看到的 vs 读接口返回的 | 差值 = **渲染兜底**（T1） |
| S2 vs S3 | 抓到的请求体 vs 读接口返回的 | 差值 = **服务端丢弃** |
| 变更审计 | **改前 / 改后 diff 整条记录**（`bx_diff`） | 看**哪些字段真的落库了** |

> **变更审计是本框架性价比最高的一招。** 它一次区分了三种可能：

| `updateTime` | 其他字段 | 目标字段 | 结论 |
| --- | --- | --- | --- |
| 未变 | 未变 | 未变 | 接口没被执行 / 打到了别的记录 |
| **变了** | **变了** | **未变** | **字段白名单缺失** |
| 变了 | 部分变 | 变了 | 成功 |

### 3.2 诱出法（Inducement）：当前端把请求拦住时

如果 T3 判定"请求根本没发出"，你是拿不到接口格式的。这时**主动篡改上游响应**，让前端校验通过，
从而**逼出那条本不会发出的请求**：

```
上游真实响应: {"字段": null}
        ↓ 代理注入
前端收到:     {"字段": "0"}     ← 字符串 "0"（T5 的通用钥匙）
        ↓
前端校验放行 → 真正发出那条 POST → 抓到完整请求体 + 接口名
```

**这是本框架最有价值的一招**：把"前端不配合"变成"前端主动交出接口格式"。
即使最终发现服务端不落该字段，这次诱出也没白做 —— 它把"哪一层丢的"从猜测变成了 diff 事实。

**纪律：诱出必须可撤、可观测、单一变量。**

- 一次只改一个字段，并**明确写出观察点**（界面显示？发包？响应码？）
- 改完先看观察点，再继续
- 注入前先记下原始响应的存档（证据不能被自己改没了）

### 3.3 找写入路径（存在性探测）

用**非破坏性**方法枚举候选接口：对候选路径发 `GET`。

- `404` → 不存在
- `405 not supported` → **存在，但只接受 POST** ← 这就是你要找的
- `200` → 已存在且可读

先打一组**对照组**（一个必然存在的路径 + 一个必然不存在的路径），拿到本地的"存在 / 不存在"
响应指纹，否则分不清 `404` 是"不存在"还是"路由没匹配"。

**Gate 3**：能写出"哪个接口、哪个字段、哪一层丢的"这样一句话。

## Phase 4 · 修复决策树【目标：用最小侵入达成用户目标】

```
                    目标字段能否写入存储（S3）？
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
   有专用写接口           有通用更新接口           无任何写接口
        │                但不落该字段                  │
        ↓                     ↓                     ↓
  直接调用写入          → 白名单缺失 → 厂商修      判断闸门 G 性质
  （诱出法拿格式）      （同时用绕过达成用户目标）        │
                                        ┌────────────┴────────────┐
                                        │                         │
                                  客户端门禁 G             服务端门禁 G
                                        │                         │
                                  响应篡改解除拦截           ❌ 停手
                                  （其余流程照常）      转人工 / 工单 / 换入口
```

**风险控制清单（写入操作前逐条过）**

| 风险 | 检查项 |
| --- | --- |
| 全字段覆盖 | 该接口是"选择性更新"还是"整行覆盖"？先用**单字段**试探 |
| 打码字段污染 | 请求体里手机号 / 身份证是打码值吗？整行覆盖会把真实值**写成星号** |
| 名字带 `save` / `insert` / `create` | 可能是插入！可能产生重复记录，**不要盲试** |
| 不可逆 | 有没有软删除？改动可回滚吗？ |
| 计费 / 权限 | 绕过的是**自检 / 展示**，还是**计费 / 资格**？后者绝对不碰 |

**Gate 4**：用户目标达成，且**没有产生任何脏数据**（或已明确记录并规划了回滚）。

## Phase 5 · 收口与交接【目标：可还原、可复现、可追责】

1. **还原环境（顺序不能错）**：先关系统代理（`bx_sysproxy off`），**再**停代理进程（`bx_proxy stop`）。
   顺序反了会在杀进程的瞬间断网 —— 还原动作本身不依赖网络，所以还能救回来，但会吓人一跳。
2. **固化证据**：全量流量存档（`.mitm`）+ 变更 diff + 精确到秒的时间线 + 复现步骤。
3. **写一份"无法推诿"的工单**（结构见下）。
4. **顺手做安全披露**：排查过程中常会发现鉴权缺陷。**只披露，不利用。**

**工单结构（让对方无法用"你重新填一下"打发你）**

| 段 | 内容 | 要求 |
| --- | --- | --- |
| 1 上下文 | 账号 ID、已完成的绑定 / 认证、客户端版本、时间戳 | 精确到可复现 |
| 2 现象 | 客观描述用户操作与反馈 | 不带情绪 |
| 3 **已排除项** | 重登 / 重装 / 换端 / 清缓存 / 换网络，逐条说明**为什么必然无效** | 堵住"你试试重装" |
| 4 证据 | 抓包结论 + **字段级前后 diff** | 数据说话 |
| 5 定位 | 指向具体接口 / 字段 / 行为 | "字段白名单不含 X" |
| 6 诉求 | 可执行的 SQL / 明确的修复项 | 别写"请尽快解决" |
| 7 附带 | 发现的安全问题 | 负责任披露 |

## 一页速记

```
症状：显示有值，但提交失败 / 提示无法完成
 └─ ① 搜响应体：提示语在不在里面？  → 定层（前端 or 服务端）
 └─ ② 抓包：请求发出了吗？
      未发出 → 前端拦截 → 诱出法（注入上游响应，逼它发包）→ 拿到接口格式
      已发出 → 读响应 + 变更审计（改前改后 diff）→ 看哪个字段被丢
 └─ ③ 目标字段能写吗？
      能写 → 直接调接口写进去（最小侵入）
      不能写 → 那道闸门是客户端门禁吗？
           是 → 篡改响应解除拦截，业务照常走
           否 → 停手，走人工 / 工单
 └─ ④ 收口：先关代理再杀进程 → 存档 → 写一份带 diff 和 SQL 的工单
```
