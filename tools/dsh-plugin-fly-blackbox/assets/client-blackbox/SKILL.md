# 客户端黑盒排查

你手上只有客户端，没有源码、没有服务端日志、没有能对话的工程师。这套框架就是为这种局面写的：
**先建模，再动手；每一步都有 Gate，没过不要往下走。**

配套资产（`Base directory for this skill:` 给出的目录下）：

| 文件 | 用途 |
| --- | --- |
| `reference/playbook.md` | 五阶段全文：动作、判据、Gate、失败了回哪一步 |
| `reference/checklist.md` | 全流程可勾选清单（含 Phase 1 自检三连） |
| `reference/case-ttw.md` | 脱敏案例：三处独立缺陷、三次转折、工单结构 |

| `code/mitm_addon_template.py` | 声明式 + 热加载的 mitmproxy addon（读 `FLY_ALLOW_INTERCEPT`） |
| `code/rules.example.json` | 规则示例（watch / patch_response / patch_request） |

## 0. 什么时候用 / 什么时候停手

**用**（命中任意两条就该上这套流程）：

- 界面**显示有值 / 显示已完成**，但提交或下一步校验始终失败；
- 提示语指向一个**用户物理上无法完成的动作**（"请先补充 X"，而 X 页面没有编辑入口）；
- 退出重登 / 重装 / 换设备 / 清缓存 / 换网络**全部无效**（症状一模一样）；
- 提示语与操作结果**互相矛盾**；
- 客服复现不了，或只会说"你重新填一下"。

**停手**（本仓的硬边界，任何一条命中就停下来问人）：

1. **wxapkg 不做**。加密容器（`V1MMWX`）的离线解开不在本仓能力内 —— 不承诺、不试、不解释成"应该能行"。
2. **不做半个代理**。TLS 拦截**没有纯仓内替代**：只转发 `CONNECT` 的代理看得到域名、看不到 body，
   而这类缺陷恰恰在 body 里（页面路由/渲染逻辑塞在 JSON 里，还有相当一部分响应体是图片、字体、gzip）。
   要么用 mitmproxy，要么以后做原生代理 —— 不拿"看得到域名"冒充"看得到内容"。
3. **不自动装依赖**。缺 mitmproxy 时把安装命令**交给用户**（两行，点名解释器），不自己 pip install。
4. **不自动提权**。`sudo` / `osascript … administrator privileges` 一律只输出成文本给人复制；
   工具侧执行前就拒绝（提权调用弹不出框、也没有超时，真会话会无超时挂住）。
5. **不碰计费、资格、身份类规则**。只绕"展示 / 自检"这类坏掉的前端逻辑。
6. **不写 `~/.dsh/skills`**，不把真实抓包与真实 ID 带进仓库。

## 1. 心智模型：三源一闸（S1 / S2 / S3 / G）

任何"填写类 / 状态类"故障，本质都是下面四个位置的值或逻辑不一致。**先写下来，再动手。**

| 代号 | 名称 | 含义 | 出错时的典型症状 |
| --- | --- | --- | --- |
| **S1** | 渲染源 | 屏幕上显示的东西 | 显示"男"，其实是 `range[0]` 兜底渲染 |
| **S2** | 提交源 | 前端真正装进请求体的值 | 校验拦住不发包；或发出去的是空值/默认值 |
| **S3** | 存储源 | 服务端真正生效的值 | 接口返回 `code:0`，字段纹丝不动 |
| **G** | 闸门 | 谁在判定"不通过" | 前端本地 `return`，还是服务端拒绝 |

**核心动作是对账（reconciliation）**：把 S1 / S2 / S3 分别取到手一一比对，同时确定 G 在哪一层。
**80% 的时间浪费，都源于把 S1 当成了 S3。**

## 2. 六条判据 T1–T6（每条：怎么测 / 什么算证伪）

| # | 判据 | 怎么测 | 什么算证伪 |
| --- | --- | --- | --- |
| **T1** | 用户看到的文字不是数据 | 界面显示 → 独立读接口取真值 | 显示值与读接口一致 ⇒ 这条陷阱不成立 |
| **T2** | 提示文案出现的位置决定责任层 | 把提示语原文丢进**全部响应体**搜 | 搜到 ⇒ 服务端判定；搜不到 ⇒ 纯前端文案 |
| **T3** | "没发出"和"发出被拒"是两种病 | 数该域名下的非 GET 请求条数 | 有保存请求 ⇒ 前端放行了，问题在服务端侧 |
| **T4** | 接口返回的可能是"回显请求对象" | 换一个**独立读接口**复核同一条记录 | 读接口与返回体一致 ⇒ 落库成功 |
| **T5** | 假值陷阱：`0` 是最贵的空值 | 用字符串 `"0"` 注入（JS 里它是真值） | 注入 `"0"` 仍被拦 ⇒ 不是 `!v` 校验的问题 |
| **T6** | 门禁分两类，一类可骗一类必须停手 | 读响应体：`confirm`/`Y`/`N`/`state` 在谁手里 | 服务端直接返回硬错误 ⇒ 服务端门禁，停手 |

**T5 的通用钥匙**：注入**字符串** `"0"`。JS 里只有 `""` 是假值，`"0"` 是真值 —— 它能同时过
`!v` 判假与 `==null` 判空，而服务端（Jackson / Gson / JSON 解析器）通常把它正常转成数字 `0`。

## 3. 五阶段（每阶段：做什么、Gate 是什么、失败回哪）

| 阶段 | 目标 | Gate | Gate 不过时回哪 |
| --- | --- | --- | --- |
| **Phase 0 症状分流** | 把症状翻译成假设 | 能用 S1/S2/S3/G 说清楚，且"为什么重登无效"有自洽解释 | 回用户的原始描述，补事实 |
| **Phase 1 建立可观测性** | 能看见每一帧流量 | **自检三连**全绿（HTTP 200 / HTTPS 200 / 目标客户端出现 `[NEW HOST]`） | 管道问题：换客户端 / 换端口 / 查 pinning |
| **Phase 2 协议测绘** | 把黑盒变成接口清单 | 能画出"操作 → 请求 → 谁判定"的流程图，并知道提示语出自哪层 | 回 Phase 1（没抓全） |
| **Phase 3 三源对账** | 定位到具体那一行 | 能写出"哪个接口、哪个字段、哪一层丢的" | 找不到写接口 → 存活性探测；前端不发包 → 诱出法 |
| **Phase 4 修复决策** | 用最小侵入达成用户目标 | 用户目标达成且**没有脏数据**（或已规划回滚） | 服务端门禁 ⇒ 停手转人工 |
| **Phase 5 收口交接** | 可还原、可复现、可追责 | 环境已还原 + 存档 + 工单可执行 | 回放过程补证据 |

**Phase 1 的自检三连**（Gate 1 的硬指标，顺序不能跳）：

```bash
# ① HTTP 能过
curl -s -o /dev/null -w '%{http_code}\n' -x http://127.0.0.1:8080 http://example.com/
# ② HTTPS 中间人能过（这一步才是真正的验证）
curl -s -o /dev/null -w '%{http_code}\n' -x http://127.0.0.1:8080 \
     --cacert .fly-blackbox/mitmproxy/mitmproxy-ca-cert.pem https://example.com/
# ③ 目标客户端确实走了代理：看日志里有没有 [NEW HOST]
tail -f .fly-blackbox/capture/all.log
```

> **在证明管道通畅之前，不要对"没抓到东西"做任何解释。** 抓不到东西的第一嫌疑永远是管道，
> 不是"目标有 pinning"。

## 4. 反模式（都是踩过的）

| # | 反模式 | 后果 | 正确做法 |
| --- | --- | --- | --- |
| 1 | 把 UI 显示当数据（T1） | 半天耗在"明明有值"上 | 回到数据源验证 |
| 2 | 不区分"没发出"与"被拒绝"（T3） | 在错误的分支上使劲 | 抓包，一秒区分 |
| 3 | 相信接口回显（T4） | 误判成功 | 独立读接口复核 |
| 4 | 用 `!v` 判断枚举（T5） | `0` 值永久不可达（很多线上 bug 的真身） | 显式判 `== null` / `=== ''` |
| 5 | 盲试 `save` / `insert` 类接口 | 数据被写坏 | 先 GET 探测方法，评估覆盖风险 |
| 6 | 一次改多个变量 | 无法归因 | 单一变量 + 明确观察点 |
| 7 | 没证明管道通就解释"没抓到" | 误判为 pinning 而放弃 | 自检三连 |
| 8 | 还原顺序颠倒（先杀进程再关代理） | 瞬断网 | 先关系统代理，再杀代理进程 |
| 9 | 忘了写还原脚本 | 留下长期代理 | 第一分钟就写 |
| 10 | 反复注销 / 重注册 / 找回 | 纯浪费时间（数据在服务端表里） | 先建模，再操作 |
| 11 | 拿前端文案当证据 | 定位错层 | 全文搜响应体（T2） |
| 12 | 把"客服复现不了"当成自己没说清 | 自责并放弃 | 用**字段级 diff** 逼他们进同一条路径 |
| 13 | 只抓不改 / 只改不验 | 拿不到结论 | 每次变更后用独立读接口复核 |
| 14 | 绕过计费 / 资格类校验 | 越界 | 只绕"展示 / 自检"，业务规则一律不碰 |

## 5. 合规红线（不可谈判）

1. **只操作你自己的账号与数据。** 不做横向探测、不碰他人 ID。
2. **不做破坏性写入。** 涉及账号资料的写入前逐条过 Phase 4 的风险清单（打码字段、整行覆盖、`save` 类接口）。
3. **不绕过计费、资格、身份类规则。** 属"业务规则"的门禁一律停手。
4. **发现漏洞 → 负责任披露**，不利用、不传播、不变现。
5. **抓包存档包含凭据**（token / 手机号 / 身份证）。归档前脱敏；发人之前打码。

## 6. 工具与资产（本包提供）

| 工具 | 干什么 | 授权 |
| --- | --- | --- |
| `bx_proxy` | 起 / 停 / 看本地拦截代理（`status` 回显状态文件、confdir、dump、`mitmdump --version`） | `start`/`stop`/`restart` 需 `FLY_ALLOW_INTERCEPT=1` |
| `bx_doctor` | 五段判决：HTTP / **HTTPS 的签发者是否就是 confdir 里的 mitm CA** / 目标客户端是否出现 / 冲突代理 / 系统代理 `Enabled` | 需 `FLY_ALLOW_INTERCEPT=1` |
| `bx_sysproxy` | 看 / 开关 macOS 系统代理（判决默认路由服务名，附一条还原命令） | `on`/`off` 需 `FLY_ALLOW_INTERCEPT=1` |
| `bx_ca` | CA 信任状态 + **要人跑的命令文本** + `security verify-cert` 事后证据 | 不受门控（永不提权） |
| `bx_flows` | 离线读 dump：`hosts` / `list` / `show` / `grep`（版本闸 + 拒绝截断） | 不受门控（只读） |
| `bx_diff` | 改前/改后字段级 diff，显式区分**缺失** / **假值** / **类型变化** | 不受门控（只读） |
| `bx_cdp_targets` | **进程内通道第一件**：列 `127.0.0.1:<port>` 上可附加的 target（page/worker/iframe）。只走回环、端口只认参数、控制通道地址不打印；整件在 `FLY_ALLOW_INTERCEPT` 门后 |
| `bx_cdp_scripts` | 附加上去收 `Debugger.scriptParsed`：**已解析**脚本清单（会回放已解析的；**不返回源码**；窗口一结束就断开） |
| `bx_cdp_coverage` | 精确覆盖率：采一段窗口 → `takePreciseCoverage` → 逐脚本"已执行字节"（区间**求并集**；拿不到快照就**大声失败**，不给半份） |

规则文件固定 `<workspace>/.fly-blackbox/rules.json`，由**你自己用文件工具写**，`bx_proxy start` 只读并校验；
schema 与"显式 off、无静默默认值"的纪律见 `reference/rules.schema.md`。
